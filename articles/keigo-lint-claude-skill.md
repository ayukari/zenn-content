Claude Code にビジネスメールを書かせると、たいていは自然な敬語になります。ただ、添削を頼んだときに定番の誤りを見落としたり、新しく書いたメールに「了解しました」が入ったりすることがあります。

この記事では、敬語の定番の誤りを**スクリプトで毎回拾い、直すかどうかの判断は Claude に任せる**スキル `keigo-email` を紹介します。MIT ライセンスで公開しています。

https://github.com/ayukari/jp-backoffice-skills

## スクリプトが拾い、LLM が判断する

敬語の正しさは文脈で変わります。そのため、すべてを機械的に決めることはできません。一方で、「おっしゃられる」のような二重敬語や、相手の行為に「拝見」を使う誤りは、文脈に関係なく誤りです。

そこで、役割を次のように分けました。

| スクリプト（keigo_lint.py） | Claude |
|---|---|
| 定番の誤りを漏れなく拾う | 相手との関係を踏まえて、直すかどうかを決める |
| 毎回同じ結果を返す | 修正版の文面を書く |

## 実際の出力

次の文を渡します。

```
部長がおっしゃられていた資料、拝見されましたか？了解しました、
明日送付させていただきます。確認させていただき、連絡させていただきます。
```

`keigo_lint.py` の実際の出力です。

```
[warn] 1行目: 「了解しました」→ 承知しました／かしこまりました（「了解」は目上・社外には失礼と受け取られることがある）
[error] 1行目: 「拝見され」→ ご覧になる（「拝見」は謙譲語。相手の行為には尊敬語を使う）
[error] 1行目: 「おっしゃられ」→ おっしゃる（二重敬語（おっしゃる＋られる））
[info] 全体: 「させていただく ×3」→ 一部を「〜いたします」「〜します」に（多用すると回りくどく読みにくい）
```

判定は3段階です。

- `error`：文脈によらず誤り。必ず直す
- `warn`：相手によっては失礼。関係を見て判断する
- `info`：好みの問題。多用していれば直す

SKILL.md には「`error` は必ず直す。`warn` と `info` は相手との関係を踏まえて判断する」と書いています。

## ルールはデータとして持つ

チェックのルールはコードに書かず、`keigo_rules.json` に並べています。現在は14件です。

```json
{"id": "ossharareru", "pattern": "おっしゃられ", "suggest": "おっしゃる",
 "why": "二重敬語（おっしゃる＋られる）", "level": "error"}
```

プログラムを書かない人でもルールを追加できます。社内でよく見る誤りを足していけば、チーム専用のチェッカーになります。

## 評価して見つかった抜け

スキルを作ったあと、実際の依頼文で評価（evals）を回しました。そこで見つかったのが次の2点です。

1. **新しく書いたメールにチェックをかけていなかった**
   SKILL.md の手順では、チェッカーを使うのは「添削時」だけでした。そのため、「催促メールを書いて」と頼まれて新しく書いたメールには、チェックがかかりません。手順を「作成時も添削時も、出力前に `keigo_lint.py` で定番の誤りを拾う」に直しました。
2. **テンプレートの件名がルールと矛盾していた**
   催促テンプレートの件名が「【再送】【元の件名】」になっていました。しかし、スキルのルールは「件名で用件と期日が分かるようにする」です。しかも【再送】は、何も再送していない場合は誤りになります。件名は「【ご確認のお願い】【用件】（【新しい期日】まで）」に変えました。

どちらも、スクリプトのテストでは見つからない問題です。スキル全体を実際の依頼で動かしてみると、手順の抜けが見えてきます。

## 使ってみる

```bash
claude plugin marketplace add ayukari/jp-backoffice-skills
claude plugin install jp-backoffice-skills@jp-backoffice
```

```
取引先の佐藤さんに、9/30締切だった見積もりの返事を催促するメールを書いて。角が立たないように。
```

スキル集には、ほかにもインボイス対応の請求書・稟議書・日報・経費帳・法令の条文検索のスキルが入っています。

スキルの設計・テスト・評価・配布の方法は、Zenn の本にまとめています（前半は無料です）。
