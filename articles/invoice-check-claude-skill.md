Claude Code に請求書を作らせると、だいたい正しいものができます。ただ「だいたい」では困るのが請求書です。この記事では、インボイス制度（適格請求書等保存方式）の要件を守らせるために作った Claude Code のスキル `invoice-jp` を紹介します。

スキルは MIT ライセンスで公開しています。

https://github.com/ayukari/jp-backoffice-skills

## LLM に任せると困るところ

適格請求書には6つの記載事項が必要です。そのなかで、LLM がよく間違えるのが次の2つでした。

1. **取引年月日**：「10/4付で」と頼むと、請求日をそのまま取引日として扱ってしまう
2. **消費税の端数処理**：端数処理は「1つの請求書につき、税率ごとに1回」と決まっているが、明細ごとに端数処理して足すことがある

2つめは、金額によっては結果が変わります。

| 明細 | 明細ごとに切り捨て | 税率ごとに1回切り捨て |
|---|---:|---:|
| 部品A 105円（10%） | 10円 | |
| 部品B 105円（10%） | 10円 | |
| 部品C 105円（10%） | 10円 | |
| 消費税額 | **30円**（誤り） | **31円**（315円×10%＝31.5円） |

1円の差ですが、請求書としては誤りです。そして LLM は、この規則を守るときと守らないときがあります。

## 方針：計算と点検はスクリプトに任せる

そこでスキルでは、次のように役割を分けました。

- **Claude**：依頼から情報を集める、足りない情報を質問する、結果を説明する
- **スクリプト**：消費税の計算、請求書の出力、既存の請求書の点検

スキルの中身は次のとおりです。

```
invoice-jp/
├── SKILL.md              # 手順とルール
└── scripts/
    ├── invoice_calc.py   # 税率ごとに1回の端数処理で計算
    ├── render_invoice.py # 同じ JSON から Markdown / HTML の請求書を出力
    └── check_invoice.py  # テキストの請求書を6項目で点検
```

スクリプトは Python の標準ライブラリだけで書いています。金額は `float` ではなく `Decimal` で計算します。

### 計算の中心

```python
for rate in sorted(totals):
    r = Decimal(rate) / 100
    base = totals[rate]                       # 税率ごとに先に合計する
    tax = (base * r).quantize(Decimal(1), rounding=rounding)  # 端数処理は1回だけ
```

テストには「間違った実装なら落ちる」例を使います。上の 105円×3 の例は、明細ごとに処理すると30円、正しく処理すると31円になるので、テストで規則を固定できます。

### 取引年月日は聞き返す

SKILL.md には「請求日と取引年月日は別物なので、取引日（または取引期間）が分からなければ必ず確認する」と書きました。スクリプトも、取引日がないまま出力するときは「取引年月日: 【要確認】」と表示します。推測で埋めさせないための二重の対策です。

## 使ってみる

インストールは2行です。

```bash
claude plugin marketplace add ayukari/jp-backoffice-skills
claude plugin install jp-backoffice-skills@jp-backoffice
```

あとはふつうに頼むだけです。

```
山田デザイン（登録番号T1234567890123）から株式会社サンプルへの請求書を作って。
10/4発行、10/1納品。Webデザイン一式10万円（税抜）と、
打ち合わせ用の菓子500円×2（軽減税率）。支払期限10/31。
```

税率ごとの集計は次のようになります（スクリプトの実際の出力から抜粋）。

```markdown
| 税率 | 対象額（税抜） | 消費税額 | 合計（税込） |
|---|---:|---:|---:|
| 8%対象（軽減税率） | 1,000 | 80 | 1,080 |
| 10%対象 | 100,000 | 10,000 | 110,000 |
```

## 既存の請求書を点検する

受け取った請求書のテキストを渡すと、`check_invoice.py` が6項目を「OK／不足／要確認」で判定します。税額は税率ごとに再計算して照合します。

```
この請求書、インボイス制度的に大丈夫？

請求書
株式会社テスト 御中
2026年10月4日
山田商店
品目 作業A 3 333 999 10%
| 10%対象 | 999 | 98 |
```

この例では、登録番号がないこと、取引年月日がないこと、消費税額が合わないことを指摘します。999円の10%は、切り捨てなら99円、四捨五入や切り上げなら100円です。98円はどの端数処理でも説明できないため、計算誤りの可能性として伝えます。

:::message
スクリプトは文字列を機械的に確認するだけです。発行者名などは目でも確認してください。経過措置や特例など、判断が必要なケースではスキルは断定しません。
:::

## 作ってみてわかったこと

- **description は機能と一致させる**：最初は「請求書・見積書・領収書」と書いていましたが、対応していたのは請求書だけでした。見積書を頼まれたときに、請求書の手順で作ろうとしてしまいます。
- **スクリプトのパスは `${CLAUDE_SKILL_DIR}` で書く**：相対パスで書くと、プラグインとして入れたときにスクリプトが見つかりません。
- **evals で「たまたま通った」を拾う**：実際の依頼文で18本の評価を回したところ、56項目中55項目が合格でした。ただ、合格のなかにもスキルの力ではなくモデルが自力で補った項目があり、それも直しました。

スキルの設計・テスト・評価・配布の方法は、Zenn の本にまとめています（前半は無料です）。
