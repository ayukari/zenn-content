この章からは、自分の業務に合わせたスキルを作ります。まずはスキルの中心になる `SKILL.md` の書き方と、スキルを正しい場面で呼び出させるための `description` の設計です。

仕様は Claude Code の公式ドキュメント（Skills）にもとづいて説明します。

https://code.claude.com/docs/en/skills

## スキルの置き場所

スキルは `SKILL.md` を含むフォルダです。置く場所によって、使える範囲が変わります。

| 置き場所 | パス | 使える範囲 |
|---|---|---|
| 個人 | `~/.claude/skills/<スキル名>/SKILL.md` | 自分のマシンのすべてのプロジェクト |
| プロジェクト | `.claude/skills/<スキル名>/SKILL.md` | そのリポジトリ（コミットすればチームで共有） |
| プラグイン | `<プラグイン>/skills/<スキル名>/SKILL.md` | プラグインを入れた人全員 |

まずは個人かプロジェクトに置いて試し、安定したらプラグインにして配布する、という流れがおすすめです（配布は7章で扱います）。

## SKILL.md の基本形

`SKILL.md` は、先頭の YAML（frontmatter）と本文でできています。

```markdown
---
name: ringi-jp
description: 稟議書（りんぎしょ）・社内決裁申請・購入申請・導入提案を、決裁者が判断しやすい構成で作成・添削する。「稟議を書いて」「決裁を取りたい」「購入申請」「ツール導入の申請」などで使う。
---

# ringi-jp: 稟議書の作成と添削

（ここに手順・ルール・出力形式を書く）
```

frontmatter の項目はすべて省略できますが、実際に重要なのは次の2つです。

- `name`：スキルの名前。省略するとフォルダ名になります。`/` メニューから手動で呼び出すときの名前にもなります。
- `description`：**何をするスキルで、いつ使うか**。Claude はこれを見て、スキルを使うかどうかを判断します。

ほかにも、自動で呼び出させない `disable-model-invocation` や、スキル実行中だけツールを許可する `allowed-tools` などがあります。必要になったときに公式ドキュメントで確認してください。

## Claude はいつ SKILL.md を読むのか

スキル設計でいちばん大事なのは、この仕組みを理解することです。公式ドキュメントでは、スキルの読み込みは2段階になっています。

1. **常に読み込まれている**：すべてのスキルの `description`
2. **呼び出されたときに読み込まれる**：`SKILL.md` の本文全体

つまり Claude は、**description だけを見てスキルを選んでいます**。本文にどれだけ良い手順を書いても、description が依頼内容と合わなければ、そのスキルは使われません。

逆に、description が広すぎると、関係ない場面で呼び出されます。

## description の書き方

公式ドキュメントのガイドは次の2点です。

- 主な用途を最初に書く
- ユーザーが実際に言いそうな言葉（トリガーになる表現）を入れる

さらに、description（と補足用の `when_to_use`）は、スキル一覧では合計 1,536 文字で切り詰められます。長く書いても後半は読まれない可能性があるので、重要なことを先頭に書きます。

このスキル集では、description を次の3つの部分で書いています。

```
[何をするか（1文）]。[使う場面・言われそうな言葉]で使う。[英語の短い説明]
```

`keigo-email` の例です。

```
日本語ビジネスメールを、相手との関係と目的に合った敬語で作成・添削する。
「メールを書いて」「敬語を直して」「お詫びメール」「催促メール」「断りのメール」などで使う。
Japanese business email writer and keigo checker.
```

最後に英語の説明を1文入れているのは、英語で依頼されたときにも選ばれやすくするためです。

### 実例：description で「できないこと」を約束していた

このスキル集を作る途中で、実際にあった失敗を紹介します。

最初の `invoice-jp` の description は「請求書・**見積書・領収書**を作成・点検する」でした。しかし、本文とスクリプトが対応していたのは請求書だけでした。

この状態では、「見積書を作って」と頼まれたときにスキルが選ばれます。そして Claude は、請求書用の手順で見積書を作ろうとします。description が**実際の機能より広い約束をしていた**わけです。

修正後の description は次のとおりです。

```
インボイス制度（適格請求書等保存方式）に対応した請求書を作成・点検する
（取引年月日・登録番号・税率ごとの消費税額などの記載漏れチェックつき）。
```

description は「できること」と完全に一致させます。将来やりたいことは書きません。

## 本文の書き方：5つの要素

本文は、Claude への作業手順書です。このスキル集では、どのスキルも次の5つの要素で書いています。

### 1. 最初に集める情報

推測で作業を始めさせないために、必要な情報と「足りなければ質問する」ことを明記します。

```markdown
## まず集める情報
足りないものだけまとめて質問する。推測で数字を作らない。

| 項目 | 例 |
|---|---|
| 費用（初期・月額・年額、税込/税抜） | 初期0円、月額11,000円（税込） |
...
```

「まとめて質問する」と書くのがポイントです。書かないと、1つずつ質問を繰り返して、何往復もかかることがあります。

### 2. 手順（番号付き）

```markdown
## 手順
1. 上の6項目の情報を集める。
2. 明細をJSONにして `${CLAUDE_SKILL_DIR}/scripts/invoice_calc.py` に渡す。
3. 請求書を出力する。
```

順番に意味がある作業は、番号付きで書きます。

### 3. ルール（よくある失敗をそのまま書く）

```markdown
## 書き方のルール
- 比較検討に「現状維持」を必ず入れる（何もしない場合のコストを示す）。
- 費用は税込か税抜かを必ず明記し、月額は年額にも換算する。
```

ルールは抽象的な心がけではなく、**実際に起きた失敗**から書くと効果があります。「丁寧に書く」ではなく「了解しました、は承知しましたにする」のように具体的にします。

### 4. 出力形式

完成形のテンプレートを載せます。Claude はそれに沿って出力するので、毎回の形がそろいます。

### 5. 判断を人に返す場所

税務・法務のように、AI が断定してはいけない部分を明記します。

```markdown
## 注意
- 税務判断が必要なケースは断定せず、税理士や国税庁の資料での確認を勧める。
- 推測した部分は【要確認】と書いて残す。
```

## 長い資料は別ファイルに分ける

公式ドキュメントでは、`SKILL.md` は500行以内に収め、詳しい資料は別ファイルに分けることを勧めています。別ファイルは、本文から参照されたときだけ読まれます。

```
keigo-email/
├── SKILL.md           # 手順とルール
├── templates.md       # 8種類のメールテンプレート
└── scripts/
    ├── keigo_lint.py
    └── keigo_rules.json
```

`SKILL.md` からは、次のように参照します。

```markdown
目的ごとのひな形は `templates.md` にある。該当するものを土台にして書き換える。
```

テンプレートは毎回すべて必要なわけではないので、別ファイルにしておくと、必要なときだけ読み込まれます。

## スクリプトのパスは `${CLAUDE_SKILL_DIR}` で書く

スキルにスクリプトを同梱するときは、パスに `${CLAUDE_SKILL_DIR}` を使います。これは `SKILL.md` があるフォルダに置き換えられる変数です。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/invoice_calc.py invoice.json
```

実はこのスキル集も、最初は `python3 scripts/invoice_calc.py` と相対パスで書いていました。この書き方では、Claude Code の作業ディレクトリがスキルのフォルダでない限り、スクリプトが見つかりません。プラグインとしてインストールした場合、作業ディレクトリがスキルのフォルダになることはまずありません。

この本を書くために公式ドキュメントを読み直して気づき、すべて `${CLAUDE_SKILL_DIR}` に直しました。手元で動いていても、配布先では動かないことがある典型的な例です。

## 設計チェックリスト

自分のスキルを書き終えたら、次の点を確認してください。

- [ ] description の先頭に主な用途がある
- [ ] description に、ユーザーが実際に言いそうな言葉が入っている
- [ ] description が、本文とスクリプトで実際にできることと一致している
- [ ] 足りない情報は「まとめて質問する」と書いてある
- [ ] ルールが具体的（実際の失敗から書いている）
- [ ] 出力形式のテンプレートがある
- [ ] AI が断定してはいけない部分を明記している
- [ ] SKILL.md が長すぎない（詳しい資料は別ファイル）
- [ ] 同梱スクリプトのパスが `${CLAUDE_SKILL_DIR}` になっている

次の章では、計算や点検を LLM に任せずにスクリプトで確実に行う方法を、`invoice_calc.py` を例に説明します。
