この章では、スキル全体の品質を evals で測る方法を説明します。前の章のテストは「スクリプトが正しく計算するか」を確かめるものでした。evals は「**スキルを使った Claude が、依頼に対して期待どおりに動くか**」を確かめます。

このスキル集で実際に evals を回し、何が見つかり、どう直したかも紹介します。

## テストと evals の違い

| | スクリプトのテスト | evals |
|---|---|---|
| 確かめるもの | スクリプトの入出力 | スキル全体（SKILL.md・資料・スクリプト）を使った応答 |
| 入力 | JSON やテキスト | ユーザーが実際に言いそうな依頼文 |
| 判定 | 自動（unittest） | チェックリストで人またはモデルが採点 |
| 見つかる問題 | 計算・判定の誤り | 手順の抜け、ルールの不足、description のずれ |

スクリプトのテストがすべて通っても、スキルとして正しく動くとは限りません。たとえば「スクリプトを呼ぶ手順が SKILL.md に書かれていない」という問題は、テストでは見つかりません。

## evals.json の形

このスキル集では、スキルごとに3つの依頼文を用意し、それぞれに「期待する動き」のチェックリストを付けています。

```json
{
  "id": "invoice-01-create",
  "skill": "invoice-jp",
  "prompt": "山田デザイン（登録番号T1234567890123）から株式会社サンプルへの請求書を作って。10/4付、Webデザイン一式10万円（税抜）、打ち合わせ時の菓子500円×2（軽減税率）。支払期限10/31。",
  "expected": [
    "invoice_calc.py / render_invoice.py を使って計算・出力している",
    "10%対象 100,000円・消費税10,000円、8%対象 1,000円・消費税80円",
    "合計 111,080円（税込）",
    "6つの必須記載事項がすべて入っている"
  ]
}
```

チェックリストは「良い請求書になっている」のような曖昧な書き方をせず、**合否が判断できる文**で書きます。金額は具体的な数字で書いておくと、採点がぶれません。

## 3種類の依頼文を用意する

スキルごとの3つの依頼文は、次の3種類に分けています。

1. **標準の依頼**：必要な情報がそろっている依頼。スキルの基本の流れを確かめます。
2. **情報が足りない依頼**：「取引先に請求書を出したい。デザイン料5万円です。」のような依頼。推測で作らず、まとめて質問するかを確かめます。
3. **やりすぎを確かめる依頼**：問題のない文章を渡して「問題ある？」と聞くような依頼。過剰な指摘をしないかを確かめます。

```json
{
  "id": "techwriting-03-no-false-positive",
  "prompt": "この文章に問題ある？『設定ファイルを開きます。`timeout` を 30 に変更します。保存して再起動します。』",
  "expected": ["大きな問題はないと答える（過剰な指摘をしない）"]
}
```

3つめは忘れられがちです。チェック系のスキルは「何か指摘しなければ」という方向に寄りやすいので、問題がないときに「問題ない」と言えるかを必ず確かめます。

## 実行と採点のしかた

手順は次のとおりです。

1. プラグインをインストールした Claude Code を、依頼ごとに新しいセッションで起動します。
2. 依頼文をそのまま入力します。
3. 応答をチェックリストと照らし合わせ、項目ごとに PASS / FAIL を付けます。
4. 結果を `evals/results/<日付>.md` に記録します。

採点は厳しめにします。このスキル集では「迷ったら FAIL」と決めました。甘く採点すると、直すべき点が残ります。

### 「たまたま通った」を記録する

採点で大事なのは、**PASS の理由**も書くことです。このスキル集の1回目の evals では、次のようなケースがありました。

- 文章チェックで、問題6つのうち3つはスクリプトが見つけ、残り3つはモデルが自分で見つけた
- カード明細の CSV で、桁区切りのカンマを正しく扱えたが、スキルにはその指示がなかった

どちらも結果は PASS ですが、スキルの力で通ったわけではありません。モデルや状況が変われば落ちる可能性があります。そこで、こうした項目は「**PASS (fragile)**」として記録し、FAIL と同じく修正の対象にしました。

## 1回目の結果と、見つかった問題

1回目の結果は **56項目中55項目が PASS**（18本中17本が全項目 PASS）でした。数字だけ見ると十分ですが、記録を読み直すと、直すべき点がいくつも見つかりました。

| 見つかった問題 | 種類 | 直し方 |
|---|---|---|
| 請求書に取引年月日の欄がない（唯一の FAIL） | スクリプトの不足 | `transaction_date` / `period` を追加し、無ければ【要確認】と出す |
| 敬語チェックを「添削時」だけ実行する手順だった | 手順の抜け | 新しく書いたメールにも必ずかける、と明記 |
| 文体チェックが「〜る。」「〜た。」の常体を見逃す | スクリプトの不足 | 常体の文末も判定するよう修正 |
| 「ユーザ」「出来る」が単独だと指摘されない | ルールの不足 | 推奨表記のルールを追加 |
| 手順書で、成功時の表示を創作しそうになる | ルールの不足 | 入力にない情報は創作せず【要確認】と書く、と追加 |
| スキルごとに「要確認」の書き方がばらばら | 表記の不統一 | すべて【要確認】に統一 |

唯一の FAIL は、請求書の必須記載事項「取引年月日」でした。依頼文にあったのは「10/4付」という請求書の日付だけで、スキルはそれを取引日として扱っていました。計算はすべて正しいのに、インボイスとしては要件を満たしていなかったわけです。こうした問題は、スクリプトのテストからは見えません。

## 2回目：スキルのフォルダの外から動かす

修正のあと、2回目では実行方法そのものを見直しました。

1回目は、スキルのフォルダの中で作業していました。しかし、プラグインとしてインストールされたスキルは、ユーザーのプロジェクトのフォルダから呼ばれます。4章で説明した `${CLAUDE_SKILL_DIR}` の問題は、まさにこの違いから起きていました。

そこで2回目は、次のようにスキルと関係のないフォルダから、絶対パスでスクリプトとテストを動かしました。

```bash
cd /tmp
P=/path/to/jp-backoffice-skills/plugins/jp-backoffice-skills/skills
for d in $P/*/scripts; do
  python3 -m unittest discover -s "$d" -t "$d"
done
python3 $P/invoice-jp/scripts/invoice_calc.py invoice.json
```

結果はすべて OK でした。軽減税率と標準税率が混ざった請求書（8%対象 1,080円 → 税額86円、105円×3 → 税額31円）も、税率ごとに1回だけ端数処理されていました。

**evals は、配布先と同じ条件で動かす**。これが2回目で得た教訓です。

## 自動で回す：claude plugin eval

この章では evals を手で回しましたが、Claude Code には evals を実行するコマンド `claude plugin eval` もあります。ヘルプ（`claude plugin eval --help`）によると、次のことができます。

- プラグインの `evals/` フォルダにある評価ケース（`case.yaml`、または `prompt.md` と採点基準 `graders/*.md`）を実行し、採点結果を出す
- プラグインを入れない状態との比較（ベースライン）を同時に行い、スコアの差を示す
- 結果を `evals/results/` に保存する

```bash
claude plugin eval ./plugins/jp-backoffice-skills
```

ケースの書き方はこの章の `evals.json` と形式が違うため、そのままでは使えません。手で回して「何を確かめるべきか」が固まったら、このコマンドの形式に移すと、修正のたびに同じ条件で回し直せます。プラグインのコードを自分のマシンで実行するので、信頼できるプラグインにだけ使ってください。

## 運用のコツ

- **スキルを直したら、関係する evals を回し直す**。直したつもりで別の項目が落ちることがあります。
- **失敗例は evals に追加する**。実際の利用で見つかった問題は、依頼文とチェックリストにして残します。同じ失敗を繰り返さないための回帰テストになります。
- **結果のファイルは日付ごとに残す**。前回との比較で、改善しているかどうかがわかります。
- **採点にサブエージェントを使ってもよい**。ただし、チェックリストは人が書き、採点の基準（迷ったら FAIL など）を明記して渡します。

## まとめ

- evals は、スキル全体を使った応答が期待どおりかを確かめる
- 依頼文は「標準」「情報不足」「やりすぎ確認」の3種類を用意する
- チェックリストは合否が判断できる文で書き、採点は厳しめにする
- 「たまたま通った」PASS は fragile として記録し、修正の対象にする
- evals は配布先と同じ条件（スキルのフォルダの外）で動かす
