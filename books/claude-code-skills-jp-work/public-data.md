最後の章では、スキルを外部の公開データとつなぎます。題材は、デジタル庁が提供する **e-Gov 法令API（Version 2）** です。法令の条文を、その場で公式のデータから取ってこられるようにします。

https://laws.e-gov.go.jp/api/2

## なぜ公開データとつなぐのか

LLM は法令についてもっともらしく答えますが、その知識には2つの弱点があります。

- **古い**：学習した時点より後の改正を知りません。消費税法のように毎年のように改正される法令では、特に問題になります。
- **正確でない**：条番号や文言を取り違えることがあります。「第57条の4」を「第57条の2」と答えても、読み手は気づきにくいものです。

業務で使うなら、条文は**公式のデータから取って、そのまま見せる**のが安全です。モデルの役割は、その条文を読んで説明することに限定します。5章の「スクリプトが拾い、LLM が判断する」と同じ考え方です。

## e-Gov 法令API v2 の基本

認証は不要で、HTTP の GET で使えます。この章で使うのは2つのエンドポイントです。

| 用途 | リクエスト |
|---|---|
| 法令を名前で探す | `GET /api/2/laws?law_title=消費税法` |
| 条文を1つ取る | `GET /api/2/law_data/{法令ID}?law_full_text_format=json&elm=MainProvision-Article_30` |

法令を探すと、法令IDや法令番号、施行日などが返ってきます。整形すると次のようになります。

```json
{
  "lawId": "363AC0000000108",
  "lawNum": "昭和六十三年法律第百八号",
  "lawTitle": "消費税法",
  "category": "国税",
  "promulgationDate": "1988-12-30",
  "enforcementDate": "2026-10-01",
  "revisionId": "363AC0000000108_20261001_507AC0000000070",
  "url": "https://laws.e-gov.go.jp/law/363AC0000000108"
}
```

「消費税法」で探すと、施行令や施行規則なども含めて複数の法令が返ってきます。どれを使うかは、`lawTitle` が完全に一致するものを選ぶか、ユーザーに確認します。

`enforcementDate`（施行日）と `revisionId`（改正の版）は、**どの時点の条文か**を示す大事な情報です。回答には必ず添えるようにします。

### 条番号の指定

`elm` には `MainProvision-Article_{条番号}` を指定します。枝番号のある条は `_` でつなぎます。

| 条文 | elm の値 |
|---|---|
| 第30条 | `MainProvision-Article_30` |
| 第57条の4 | `MainProvision-Article_57_4` |

ユーザーは「第57条の4」のように書くので、スクリプトで `57_4` に変換します。

```python
import re

def normalize_article_num(s):
    """'第57条の4' / '57の4' / '57_4' -> '57_4'"""
    s = s.strip().translate(str.maketrans("０１２３４５６７８９", "0123456789"))
    m = re.fullmatch(r"第?(\d+)条?(?:の(\d+))?", s) or re.fullmatch(r"(\d+)_(\d+)", s)
    if not m:
        raise ValueError(f"条番号を解釈できません: {s}")
    return "_".join(g for g in m.groups() if g)
```

漢数字（「第三十条」）にも対応する場合は、変換表を追加します。

### 条文の JSON を読みやすくする

条文は、`Article`（条）→ `Paragraph`（項）→ `Item`（号）という木構造の JSON で返ってきます。そのままでは Claude にも人にも読みにくいので、項と号をテキストに整形します。消費税法 第30条を整形すると、先頭は次のようになります（全13項）。

```
第三十条（仕入れに係る消費税額の控除）
事業者（第九条第一項本文の規定により消費税を納める義務が免除される事業者を除く。）が、
国内において行う課税仕入れ（…）若しくは特定課税仕入れ又は保税地域から引き取る課税貨物
については、…
```

整形の処理は、木をたどって `Sentence` の文字列をつなげるだけです。

```python
def text_of(node):
    if isinstance(node, str):
        return node
    return "".join(text_of(c) for c in node.get("children", []))

def find(node, tag):
    for c in node.get("children", []):
        if isinstance(c, dict) and c.get("tag") == tag:
            return c
    return None
```

## スキルにする

この処理を、スキルに同梱するスクリプトにまとめます。ここで示す `houki-lookup` は設計例で、2〜3章のスキル集にはまだ含まれていません。構成は次のとおりです。

```
houki-lookup/
├── SKILL.md
└── scripts/
    ├── law_lookup.py       # 検索・条文取得・整形（標準ライブラリのみ）
    └── test_law_lookup.py  # 記録した API 応答で整形をテスト
```

SKILL.md の中心は次のとおりです。

````markdown
---
name: houki-lookup
description: 日本の法令の条文を e-Gov 法令API から取得し、原文を示したうえで説明する。「消費税法30条を見せて」「インボイスの義務は何条？」「この規定の根拠条文は」などで使う。
---

## 手順
1. 法令名と条番号を確認する。条番号が不明なら、法令名だけで検索し、
   候補の条をユーザーと確認する。推測で条番号を決めない。
2. 次のスクリプトで条文を取得する。
   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/law_lookup.py --title 消費税法 --article 57の4
   ```
3. 取得した条文を **原文のまま** 引用し、そのあとに説明を書く。
4. 回答の最後に、法令名・条番号・施行日・e-Gov の URL を書く。

## ルール
- 条文の文言は、スクリプトの出力以外から書かない。
- 取得に失敗したら、記憶で条文を補わず、失敗したことを伝える。
- 具体的な事案への当てはめは断定せず、専門家への確認を勧める。
````

ポイントは「**取得に失敗したら、記憶で補わない**」というルールです。これがないと、API に接続できなかったときに Claude が自分の知識で条文を「再現」してしまいます。見た目では区別がつかないので、必ず明記します。

### テストは記録した応答で行う

公開 API に毎回アクセスするテストは、遅く、相手のサーバーにも負担をかけます。実際の応答を一度だけ保存し、テストではそのファイルを使います。

```python
class TestNormalize(unittest.TestCase):
    def test_article_30(self):
        data = json.load(open(FIXTURES / "law_data_shohizei_art30.json"))
        a = normalize_article(data)
        self.assertEqual(a["articleTitle"], "第三十条")
        self.assertEqual(a["articleCaption"], "（仕入れに係る消費税額の控除）")
        self.assertEqual(len(a["paragraphs"]), 13)
```

## 公開 API を使うときのマナー

- **間隔をあける**：連続してリクエストするときは、0.5秒以上あけます。
- **User-Agent を設定する**：何のツールからのアクセスかがわかるようにします。
- **再試行は控えめに**：失敗したら数回だけ、間隔を広げながら試します。
- **利用規約を確認する**：データの出典の書き方などは、e-Gov の利用規約に従います。

## 社内ネットワークで使えない場合

会社のネットワークやクラウドの実行環境では、外部への接続が許可制になっていることがあります。この本を書いている環境でも、`laws.e-gov.go.jp` への接続は許可の設定が必要でした。

スキルを配る前に、使う人の環境から API に接続できるかを確かめてください。接続できない場合の選択肢は2つあります。

1. 情報システム部門に `laws.e-gov.go.jp` への接続許可を依頼する
2. 同じ処理をクラウドで動かし、その結果を使う

2つめの例として、この章のスクリプトとほぼ同じ処理を、スクレイピング基盤の Apify 上で動くアクター（Actor）にしました。ソースコードは GitHub で公開しています。

https://github.com/ayukari/apify-jp-law-search

## ほかの公開データ

同じ方法で、ほかの公的なデータともつなげられます。

| データ | 使いみちの例 |
|---|---|
| 国税庁 適格請求書発行事業者公表サイトの Web-API | 請求書の登録番号が実在するかを確かめる（`invoice-jp` の拡張） |
| 国税庁 法人番号システムの Web-API | 取引先の正式名称・所在地を確かめる |
| 内閣府の「国民の祝日」CSV | 支払期日が休日にあたるかを確かめる |

国税庁の Web-API は、利用にアプリケーションIDの申請が必要です。申請や利用条件は、それぞれの公式サイトで確認してください。

## まとめ

- 法令のように変わる情報は、モデルの知識ではなく公式のデータから取る
- e-Gov 法令API v2 は認証不要で、法令の検索と条文の取得ができる
- 条文は原文のまま引用し、施行日と出典を必ず添える
- 「取得に失敗したら記憶で補わない」をルールに明記する
- テストは記録した応答で行い、公開 API には負担をかけない

## おわりに

この本では、日本の事務作業向けのスキル集を題材に、スキルを使う・作る・確かめる・配る・育てる方法を説明しました。

スキルの価値は、**あなたの業務の知識を、毎回同じ品質で Claude に使わせられる**ことにあります。完璧なものを最初から作る必要はありません。いちばん面倒な作業を1つ選び、小さなスキルを作るところから始めてみてください。
