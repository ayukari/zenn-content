この章では、請求書以外の3つのスキルを使います。敬語メール、稟議書、日報です。どれも「型」と「よくある失敗」がはっきりしている文書で、スキルにすると効果が大きい分野です。

## 敬語メール（keigo-email）

### 書いてもらう

```
取引先の佐藤さんに、9/30締切だった見積もりの返事がまだ来てないので
催促メールを書いて。角が立たないように。
```

`keigo-email` スキルは、まず次の3点を決めます。相手との関係（社外・取引中）、目的（催促）、トーン（丁寧）です。そのうえで、スキルに入っている8種類のテンプレート（依頼／催促／お詫び／お断り／お礼／日程調整／報告／初めての連絡）から催促用を選んで書き始めます。

催促テンプレートには、角を立てないための要素が最初から入っています。

- 件名で用件と新しい期日が分かる（例：【ご確認のお願い】お見積りの件（10/7まで））
- 元の依頼日・期日・対象を具体的に書く
- 「本メールと行き違いでご対応いただいておりましたら、ご容赦ください」を入れる
- 新しい期日をはっきり示す

### 添削してもらう

自分で書いたメールを直してもらうこともできます。

```
このメール直して：
『部長がおっしゃられていた資料、拝見されましたか？了解しました、
明日送付させていただきます。確認させていただき、連絡させていただきます。』
```

スキルは、まず敬語チェッカー `keigo_lint.py` で定番の誤りを拾います。実際の出力は次のとおりです。

```
[warn] 1行目: 「了解しました」→ 承知しました／かしこまりました（「了解」は目上・社外には失礼と受け取られることがある）
[error] 1行目: 「拝見され」→ ご覧になる（「拝見」は謙譲語。相手の行為には尊敬語を使う）
[error] 1行目: 「おっしゃられ」→ おっしゃる（二重敬語（おっしゃる＋られる））
[info] 全体: 「させていただく ×3」→ 一部を「〜いたします」「〜します」に（多用すると回りくどく読みにくい）
```

`error` は必ず直す誤りです。`warn` と `info` は相手との関係しだいで判断します。Claude はこの結果をもとに、文脈を読んで修正版と変更点の一覧を出します。

チェッカーのルールは `keigo_rules.json` に書かれています。自分の会社でよく見かける誤りを追加することもできます（ルールの作り方は5章で扱います）。

## 稟議書（ringi-jp）

稟議書は「決裁者がこの書類だけで承認してよいか判断できる」ことが目的です。`ringi-jp` スキルは、次の構成で書きます。

1. 申請内容（結論）
2. 目的・背景
3. 費用（税込か税抜かを明記し、月額は年額にも換算する）
4. 期待される効果（できるだけ数字で）
5. 比較検討（**現状維持**を必ず含める）
6. リスクと対策
7. スケジュール
8. 添付資料

```
経理部で請求書の受け取りを月100件手入力してて、月30時間かかってる。
月額3万円（税抜）のクラウド請求書受領サービスを入れたい。稟議書を作って。
```

このように頼むと、スキルは結論から書き始めます。費用は年額36万円（税抜）に換算し、比較表には「現状維持：追加費用0円、ただし月30時間の作業が続く」を入れます。

逆に、情報が足りない頼み方をした場合はどうでしょうか。

```
新しいツール入れたいから稟議書いて
```

スキルは推測で書き始めずに、ツール名・費用・目的・期待効果・決裁希望日をまとめて質問します。稟議書の数字を AI が勝手に作ってしまうと、あとで困るのは申請した本人だからです。

既存の稟議書を渡すと、次の6つの観点で「OK／要修正」の表を作って添削します。

- 結論が1章だけで分かるか
- 金額・税込/税抜・期間が明確か
- 効果に数字があるか
- 比較検討（現状維持を含む）があるか
- リスクと対策が対になっているか
- 決裁希望日とその理由があるか

## 日報・週報（nippo-jp）

日報の読み手が知りたいのは「予定どおりか」「手助けが必要か」です。`nippo-jp` スキルは、作業の羅列ではなく**結論・成果・課題・次の予定**を短く書きます。

```
今日の日報書いて。A社見積作った、送った。B社と打ち合わせ、来週デモ。
C社の請求書の金額が違うって連絡あった、まだ調べてない。
明日はC社の件とD社提案書。
```

このメモから、スキルは次のような日報を作ります。

- **ひとこと**：A社見積は送付済み、C社の請求金額の件で確認が必要
- **今日やったこと**：A社の見積書を作成・送付、B社と打ち合わせ（来週デモ実施）
- **課題・相談**：C社から請求金額が違うとの連絡あり、未調査
- **明日の予定**：C社の請求金額の確認、D社提案書の作成

ポイントは「A社対応」ではなく「A社の見積書を送付」と**成果で書く**ことです。もう1つのポイントは、メモにない事実を足さないことです。推測が必要な部分には【要確認】を付けて残します。

1週間分の日報をまとめて渡すと週報にもなります。同じ案件は最新の状況だけを残し、何度も出てきた未解決の課題は「課題・リスク」に上げます。

## まとめ：スキルが守らせていること

ここまでの3章で使ったスキルには、共通する設計があります。

| 共通の設計 | 例 |
|---|---|
| 型（構成）を決めておく | 稟議書の8章構成、日報のひとこと→成果→課題→予定 |
| よくある失敗をルールにする | 二重敬語、税率ごとの端数処理、現状維持の比較 |
| 機械的に判定できることはスクリプトに任せる | 消費税の計算、請求書の点検、敬語チェック |
| 推測で埋めずに質問する | 稟議書の数字、家事按分、取引日 |

後半の4章からは、この設計を**自分の業務**に当てはめてスキルを作る方法を解説します。扱う内容は次のとおりです。いずれも、このスキル集の実際のコードと評価結果をもとに説明します。

- SKILL.md の書き方と、description でスキルを正しく呼び出させるコツ（4章）
- 計算や点検をスクリプトに任せる方法（5章）
- evals で品質を測って直す流れ（6章）
- プラグインとしての配布とバージョン管理（7章）
- チームの業務スキル集の設計（8章）
- 法令API などの公開データとのつなぎ方（9章）
