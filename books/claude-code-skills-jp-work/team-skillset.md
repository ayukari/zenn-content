ここまでで、スキルを作り、テストし、配布するしくみがそろいました。この章では、それを使って**自分のチーム専用のスキル集**を設計します。架空の「経理チーム（5人）」を例に、どの業務をスキルにするか、どう共有し、どう育てるかを順に考えます。

## 1. どの業務をスキルにするか

最初にやることは、業務の棚卸しです。チームで1週間、「Claude に頼めたら楽だった作業」をメモしてもらい、次の表で評価します。

| 観点 | 質問 | 高いほどスキル向き |
|---|---|---|
| 頻度 | 週に何回あるか | 毎日・毎週ある |
| 型 | 毎回同じ形・同じ手順か | 書式や手順が決まっている |
| 間違いの痛さ | 間違えると何が起きるか | 金額・期日・法令に関わる |
| 属人性 | 特定の人しかできないか | 「〇〇さんに聞かないとわからない」 |

経理チームの例では、次のような結果になりました。

| 業務 | 頻度 | 型 | 痛さ | 属人性 | 判断 |
|---|---|---|---|---|---|
| 請求書の作成・点検 | 高 | 高 | 高 | 中 | **スキル化**（既存の invoice-jp を使う） |
| 経費の仕訳 | 高 | 中 | 中 | 高 | **スキル化**（expense-ledger-jp を拡張） |
| 支払依頼書の作成 | 中 | 高 | 高 | 高 | **新しく作る** |
| 取引先への催促メール | 中 | 中 | 中 | 低 | keigo-email をそのまま使う |
| 月次決算の段取り | 低 | 中 | 高 | 高 | 後回し（手順書を先に作る） |

ポイントは、**すべてを自作しない**ことです。この本のスキル集のように公開されているものは、そのまま使うか、必要な部分だけ拡張します。チームで作るのは、チーム固有の部分だけにします。

月次決算のように頻度が低く、手順もまだ固まっていない業務は、いきなりスキルにしません。まず人が読む手順書を作り、それが安定してからスキルにします。

## 2. 構成：共通パックとチームパック

スキルが増えてきたら、2層に分けると管理しやすくなります。

```
共通パック（全社）              チームパック（経理）
├── keigo-email                 ├── shiharai-irai     支払依頼書
├── ringi-jp                    ├── keihi-rules       自社の経費規程
└── nippo-jp                    └── torihikisaki      取引先ごとの注意点
```

- **共通パック**：どのチームでも使う文章系のスキル。この本のスキル集をそのまま使ってもかまいません。
- **チームパック**：そのチームの規程や取引先情報を含むスキル。**社外に出さない**ので、非公開リポジトリに置きます。

7章で説明した marketplace.json には複数のプラグインを並べられます。1つの非公開リポジトリに「共通」と「経理」のプラグインを並べ、チームごとに必要なものだけを入れる、という運用もできます。

## 3. チーム全員に配る

プロジェクトの `.claude/settings.json` にマーケットプレイスとプラグインを書いておくと、そのリポジトリで作業するメンバーにプラグインを案内できます。

```json
{
  "extraKnownMarketplaces": {
    "keiri-skills": {
      "source": { "source": "github", "repo": "your-org/keiri-skills" }
    }
  },
  "enabledPlugins": {
    "keiri-pack@keiri-skills": true
  }
}
```

個人で入れる場合は、7章の2行（`marketplace add` と `install`）を手順書に載せておきます。`install` の `--scope project` を使うと、プロジェクトの設定に書き込まれます。

非公開リポジトリのマーケットプレイスを使うには、メンバーそれぞれがそのリポジトリを読める必要があります。GitHub のチームの権限で管理しておきます。

## 4. 社内ルールは「データ」として持つ

チームパックで最も価値があるのは、**社内ルールや取引先ごとの注意点**です。これを SKILL.md の文章に埋め込むと、ルールが変わるたびにスキルの書き直しが必要です。

5章の敬語チェックと同じように、ルールは別ファイルのデータにします。

```
keihi-rules/
├── SKILL.md
├── rules.json        # 勘定科目の判定ルール（経理担当が更新）
└── scripts/
    └── check_keihi.py
```

```json
[
  {"pattern": "タクシー", "account": "旅費交通費",
   "note": "22時以降の帰宅は上長承認が必要（経費規程 第8条）"},
  {"pattern": "書籍", "account": "新聞図書費",
   "note": "1万円以上は資産計上の確認"}
]
```

こうしておくと、プログラムを書かない経理担当者でもルールを更新できます。規程が改定されたら、この JSON を直してプルリクエストを出すだけです。

## 5. 新しいスキルを作る：支払依頼書の例

チーム固有の新しいスキルは、4章の5つの要素で設計します。支払依頼書（shiharai-irai）の場合は次のとおりです。

| 要素 | 内容 |
|---|---|
| 最初に集める情報 | 支払先・金額（税込/税抜）・支払期日・請求書番号・予算科目・承認者 |
| 手順 | 1. 情報を集める 2. 金額をスクリプトで検算 3. 書式に流し込む 4. 承認ルートを示す |
| ルール | 請求書と金額が1円でも違えば止める。振込先の変更依頼が書かれていたら、作成を止めて電話確認を促す |
| 出力形式 | 社内の支払依頼書テンプレート |
| 人に返す判断 | 予算超過の可否、例外的な支払条件 |

「振込先の変更依頼」のルールに注目してください。振込先変更を装った詐欺は、経理業務の大きなリスクです。**人が見落としやすい危険を、スキルが毎回確実に止める**。これはチーム専用スキルならではの価値です。

## 6. 育てる：運用のルール

スキル集は、作って終わりではありません。経理チームの例では、次のルールで運用します。

- **持ち主を決める**：スキルごとに担当者を1人決め、README に書きます。
- **変更はプルリクエストで**：SKILL.md・ルール・スクリプトの変更は、担当者がレビューします。
- **失敗は evals に追加する**：「スキルが間違えた」と報告があったら、その依頼文を evals に足してから直します（6章）。
- **月に1回、evals を回す**：モデルの更新でふるまいが変わることがあるため、定期的に確かめます。
- **使われていないスキルは消す**：description が他のスキルとぶつかり、誤って呼び出される原因になります。

### 機密情報の扱い

チームパックには、取引先名や社内規程が入ります。次の点を守ってください。

- 非公開リポジトリに置き、権限はチーム単位で管理する
- 個人情報（従業員の口座番号など）はスキルに書かない。必要なら実行時に入力してもらう
- 例文には架空の会社名・金額を使う
- 会社の生成 AI 利用ルールがある場合は、それに従う

## まとめ

- 業務を「頻度・型・間違いの痛さ・属人性」で評価し、スキルにするものを選ぶ
- 公開されているスキルはそのまま使い、チーム固有の部分だけを作る
- 共通パックとチームパックの2層にし、チームパックは非公開にする
- 社内ルールはデータとして分け、プログラムを書かない人でも更新できるようにする
- 持ち主・レビュー・evals のルールを決めて、スキル集を育てる
